# Worktree Isolation Invariant

<architectural_invariants>
- **Write sessions use a worktree.** Run your worktree-start flow before making changes. `.claude/hooks/worktree-gate.sh` enforces this on `Write|Edit`, scoped to the source directories in `ff.config.json` under `worktree.guardedPaths` (`sigint101/`) — docs, `tests/` and notes are deliberately outside it, because a gate that fires during note-taking teaches you to bypass it. Override via `SKIP_WORKTREE_GATE=true`: Tier 1, confirmed with the user, never for multi-file feature work.
- **That gate fails OPEN when git cannot answer, and says so on stderr.** Unlike the flash gate it protects a workflow convention rather than a disk: a misplaced commit is recoverable, whereas blocking on an unanswerable git question would leave a session unable to write to source at all — and an env-var bypass cannot be injected into a running session. That is the deadlock in `bypass-governance.md`. Failing open is the right direction here; failing open *silently* would not be.
- **Read-only sessions can share the main checkout.** Reviews, debugging, exploration, and plan mode don't need a worktree — hooks that block only writes and commits won't get in the way.
- **Run setup after entry.** After creating a worktree, run your setup step: link shared dependencies, copy env, build any per-branch artifacts, write an activity timestamp.
- **NEVER track a symlinked local-only directory.** If a dev-process directory is a *symlink* into a separate local-only repo (no remote), tracking any file under it converts the symlink back into a real directory, and setup then silently skips symlink re-creation — so worktree removal permanently loses every uncommitted file under it. Write under it freely; never `git add` it.
- **Build-output directories are NEVER symlinked.** Unlike shared dependency directories (a single lockfile, safe to symlink), compiled build output is branch-specific. Symlinking it causes one branch's build to overwrite another's, dangling symlinks when temporary worktrees are cleaned up, and stale-artifact failures. Each worktree builds its own.
- **Don't run `git worktree remove` on your own CWD.** Removing the worktree you're inside breaks git and forces a restart. Change directory out first, then remove.
- **Discard is only safe for durably-stored state — verify remotes before discarding.** Discarding changes on worktree removal throws away anything not on a durable remote. Two failure modes, each a real data-loss risk: (1) a commit made *after* the last push — a "re-commit only uncommitted changes" cleanup flow never re-pushes it; (2) uncommitted edits in a local-only directory (no remote → no recovery path). Before any discard: verify `git log origin/<branch>..HEAD` is empty (else push), AND any local-only directory is clean (else commit it separately).
- **NEVER remove worktrees from other sessions.** A worktree may be active work-in-progress from a concurrent session. Only remove worktrees your session created. If one looks stale, check its age and activity, then ask the user before removing — a forced remove destroys uncommitted work permanently.
- **Naming convention.** Use descriptive names that include the purpose (e.g. `fix-auth-tests`), not generic names like `temp`. The name becomes the branch name.
</architectural_invariants>

## Merge Gotchas

- **`git merge` reports "Already up to date" even when the branch has unique commits.** If a worktree branched from HEAD and the main tree received no new commits before the merge, the merge base IS the branch point. Verify with `git log --oneline main..<branch>`; if it shows commits, the merge will fast-forward.
- **A clean `git merge-tree` does NOT mean the integrated result is semantically compatible.** When consolidating tangled parallel branches onto one integration branch, each merging clean into main individually (and a clean textual `merge-tree`) is necessary but NOT sufficient. A latent *contract* conflict survives a clean textual merge: e.g. branch A hardcodes a list of files that must carry a token while branch B moves that token elsewhere — git merges both with zero conflict markers, but a contract test goes red on the integrated result. Run the full contract/meta test suite on the integration branch before landing.
- **`gh pr close --delete-branch` fails to delete a branch checked out in another worktree.** It closes the PR and attempts the *remote* branch delete, but the local branch (in use by a worktree) blocks the delete mid-way, leaving the operation half-done. Finish with an explicit remote-branch delete *after* the worktree is removed.
